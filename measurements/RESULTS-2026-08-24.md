# Device results — 2026-08-24

S25+ (SM-S936N) · Adreno 830 · Turnip (Mesa 26.1.0-devel) · inside Winlator.

## Stage 4 — queue topology: hypothesis CONFIRMED

```
family0  count=1  tsBits=48  GRAPHICS+COMPUTE+TRANSFER+SPARSE_BINDING
family1  count=1  tsBits=48  SPARSE_BINDING
separate queues possible : False
```

**One usable queue.** D3D12's direct, compute and copy queues all serialise
onto it. Texture streaming cannot overlap rendering.

Confirmed on hardware, matching what the Turnip capture implied. This is now
a measured fact rather than a hypothesis, and the first concrete Star Bionic
target.

## Stage 4b — what the single queue actually costs

Measured with `vkbench` queue-cost, 32 iterations, 1024 workgroups per
dispatch, 8 MB copied per iteration. GPU time from timestamp queries.

| | GPU ms |
|---|---|
| render only | 16.69 |
| upload only | 28.57 |
| **serial sum** | **45.27** |
| **interleaved** | **32.95** |

**`overlap_fraction: 0.272`** — the driver pipelines despite the single queue.
27% of the upload time is absorbed, not paid twice.

A second run measured **0.382** (render 23.16, upload 35.42, interleaved
36.18). So overlap varies run to run between roughly 0.27 and 0.38, and in
the second run `interleaved` ≈ `upload_only`, meaning the render work hid
almost entirely inside the uploads. Partial overlap is reproducible; its
exact size is not.

**This softens the Stage 4 conclusion.** The topology finding stands — there
is one usable queue and D3D12's three queue types must share it — but they do
*not* fully serialise. Turnip overlaps within the queue.

What it still costs: uploads add **16.26 ms on top of 16.69 ms of render**,
roughly **doubling** frame cost under heavy streaming. Real, and worth
attacking, but not the catastrophe a fully serialised queue would have been.

Priority accordingly: **demoted from the first Star Bionic target to a
measured, moderate cost.** Whether it matters for FH6 depends on how much the
game actually streams per frame, which is unmeasured.

Caveat: compute dispatches and buffer copies are a proxy for render and
texture streaming. This bounds the effect; it does not predict FH6's frames.

## Stage 8/10 — GPU throughput, and a test that was too easy

| workgroups | GPU ms | implied fps | fits 60 Hz |
|---|---|---|---|
| 64 | 0.04 | 28,324 | yes |
| 256 | 0.10 | 10,294 | yes |
| 1,024 | 0.35 | 2,879 | yes |
| 4,096 | 1.33 | 751 | yes |
| 16,384 | 5.28 | 189 | yes |

**Every level fit, so the test found nothing.** At maximum load the GPU used
32% of a 60 Hz frame budget. The ladder was calibrated against the CPU
rasterizer used for validation, where 16,384 workgroups took 74.70 ms — the
Adreno does the same work **14x faster**.

Fixed: the sweep now **doubles until the budget is actually exceeded**. The
re-run found the threshold — and something more important.

### Re-run with the adaptive sweep

| workgroups | avg ms | min | max | spread | µs/group | 60 Hz avg / worst |
|---|---|---|---|---|---|---|
| 64 | 0.030 | 0.030 | 0.030 | 0.0% | 0.469 | yes / yes |
| 1,024 | 0.304 | 0.303 | 0.305 | 0.7% | 0.297 | yes / yes |
| 16,384 | 4.640 | 4.636 | 4.643 | 0.2% | 0.283 | yes / yes |
| **65,536** | **14.994** | 11.859 | **18.506** | **44.3%** | 0.229 | **yes / NO** |
| 262,144 | 33.636 | 27.402 | 44.195 | 49.9% | 0.128 | NO / NO |

`groups_at_60hz_budget: 83,172` — the average crosses 16.67 ms there.

### The real finding: consistency collapses before the average does

Frame-time spread is **0.2% up to 16,384 workgroups and 44% at 65,536**. It
does not degrade gradually; it falls apart the moment the GPU is genuinely
loaded. Almost certainly DVFS — the clock moving under sustained load.

At 65,536 workgroups the average is 14.99 ms, which is 66.7 FPS and inside
the budget. The worst frame is 18.51 ms, which is **54 FPS and is not**.

**That is a benchmark reporting "fits 60Hz" for a workload that visibly
stutters.** Exactly the failure the profiler doc warned about when it said
p95 matters more than mean for sustained load — and this tool was making it.

Fixed: `fits_60hz_budget` is split into `fits_60hz_avg` and
`fits_60hz_worst`, spread is reported per level, and a new
`groups_consistently_under_60hz` records the highest level whose *worst*
frame still fit. The gap between that and the average threshold is precisely
the region where mean FPS lies about playability.

**For FH6 this reframes the target.** The question is not "can Adreno 830
average 60 FPS at 1080p High" — the GPU has ample headroom. It is whether it
can hold frame time steady once it is working hard, and the answer measured
here is that consistency degrades sharply well before throughput runs out.

### Efficiency improves with load

µs per workgroup falls from 0.469 to 0.128 as load rises. The GPU is
launch-bound at low occupancy and only reaches full efficiency under heavy
load — so light synthetic tests understate it, which is part of why the
first fixed ladder found nothing.

The timestamp path is validated: `timestampPeriod` 52.083 ns, GPU times
monotonic across four orders of magnitude.

## Stage 5 — pipeline cache: works, and the win is enormous

| Pass | Wall | Per pipeline | Cache hits |
|---|---|---|---|
| cold (empty cache) | 89.10 ms | 1.86 ms | 0 / 48 |
| warm (same cache) | 0.12 ms | ~0 | **48 / 48** |
| **seeded from blob** | **0.14 ms** | ~0 | **48 / 48** |

Cache blob: **244,765 bytes** for 48 pipelines (~5 KB each).
Speedup: **~640x**.

`seeded_from_blob` is the case that matters — a cache serialised, written to
disk, and reloaded in a *later process*. It gets 48/48 hits, so a persistent
on-disk pipeline cache works completely on this driver.

`cache_hits = 48` is what makes this trustworthy. The lavapipe validation run
showed a 1.35x wall-time drop with `cache_hits = 0` — warm-up masquerading as
caching. Here the hits are real.

**Extrapolation, clearly labelled as such:** at 1.86 ms/pipeline, a title
with ~5,000 pipelines would spend roughly **9 seconds** compiling on a cold
run and produce a ~25 MB cache. FH6's actual pipeline count is unknown; this
is arithmetic on a measured per-pipeline cost, not a measurement of FH6.

## Stage 7 — memory: the earlier reading was wrong

```
initial budget    2.80 GiB
allocated total   4.00 GiB     <- 43% MORE than the "budget"
hit failure       False        <- stopped at OUR cap, not the driver's limit
usage tracked     True
```

| allocated | budget | usage | headroom |
|---|---|---|---|
| — | 2.80 | 0.00 | 2.80 |
| 128 MB | 2.88 | 0.12 | 2.76 |
| 1024 MB | 3.02 | 1.00 | 2.02 |
| 2048 MB | 3.45 | 2.00 | 1.45 |
| 3072 MB | 4.28 | 3.00 | 1.28 |
| 4096 MB | 5.10 | 4.00 | 1.10 |
| after free | 4.70 | 0.00 | 4.70 |

### Correction

[Stage 2b](../docs/03-turnip-capabilities.md) called 2.80 GiB "the usable
budget" and "the hardest measured constraint". **That was wrong.**

`heapBudget` is not a ceiling. Per the extension, it is an *estimate of how
much this process may allocate*, and Mesa computes it as roughly
`usage + estimated remaining`. So it **rises** as you allocate. We exceeded
the initial figure by 43% without a single failed allocation.

The meaningful derived number is **headroom = budget − usage**, which fell
2.80 → 1.10 GiB across the run. That is what predicts where allocation stops.

`usage_tracked_allocations: true` — usage moved exactly in step with what we
allocated (0.12, 1.00, 2.00, 3.00, 4.00 GiB). The instrumentation is real,
unlike lavapipe's, so headroom can be trusted as a live signal.

### Second run — the ceiling, found destructively

Re-run with a 10 GiB cap. Initial budget this time was **3.85 GiB**, not
2.80 — confirming the figure is environmental, not a device property.

| allocated | headroom |
|---|---|
| 128 MB | 3.78 GiB |
| 1024 MB | 2.98 |
| 2048 MB | 2.10 |
| 3072 MB | 1.51 |
| 4096 MB | 0.88 |
| 5120 MB | 0.70 |
| 6144 MB | 0.74 |
| **7168 MB** | **0.53** |

**7.00 GiB allocated successfully. Then the container was killed** — the JSON
ends mid-object because the process died while writing it.

So Winlator reaches at least 7 GiB of Vulkan device memory. Vulkan device
memory is a **native** allocation and is not bound by Android's Java heap
limit, which is consistent with large native consumers (LLM runtimes, heavy
games) reaching ~9 GB on this class of device.

Note the headroom curve is not monotonic — 0.88 → 0.70 → 0.74 → 0.53. The
driver's estimate moves as the system reclaims memory elsewhere, so it is a
noisy signal, not a clean countdown.

### The test had a design flaw

It allocated until the driver refused. **On Android the driver never
refuses** — the low-memory killer takes the whole container first, so the
loop had no reachable exit and took the container down with it.

Fixed: allocation now stops while `--headroom-floor-mb` (default 1024) of
headroom remains, checked on **every** step rather than every eighth, so it
cannot step past the cliff between samples. Reported steps are flushed
immediately, and `bench-report.py` repairs a truncated file rather than
refusing it.

### Third run — clean, with the safety valve

```
stopped_on_headroom_floor : true
hit_allocation_failure    : false
hit_cap                   : false
allocated                 : 4.75 GiB   (headroom 1.07 GiB at stop)
```

Stopped on the floor, no crash, container intact. The valve works.

### What three runs actually establish

| run | initial budget | allocated | how it ended |
|---|---|---|---|
| 1 (4 GiB cap) | 2.80 GiB | 4.00 GiB | hit our cap |
| 2 (10 GiB cap) | 3.85 GiB | **7.00 GiB** | container killed |
| 3 (1 GiB floor) | 3.30 GiB | 4.75 GiB | stopped cleanly |

**The initial budget is meaningless as a planning number.** Three readings on
the same device: 2.80, 3.85, 3.30 GiB. It reflects whatever else Android was
holding at that instant, and every run exceeded it.

**Headroom at the same allocation differs run to run too** — at 4096 MB it
read 1.10, 0.88 and 1.48 GiB. So headroom is a usable *live* signal for
backing off, but not a figure to design a memory budget around.

**The only hard number is run 2: ~7 GiB reached, then the container died.**
That is the practical ceiling, and it is a ceiling enforced by Android's
low-memory killer rather than by Vulkan.

### Consequence for FH6

A 1080p/High target on a Forza-generation title plausibly wants 4–6 GB. That
fits under ~7 GiB — but the margin is thin and depends entirely on what else
the phone is doing. Stage 7 should therefore:

- read headroom **live** and back off, rather than plan against a fixed budget
- treat anything under ~1 GiB headroom as the danger zone, since past that
  the failure is a process kill, not a failed allocation

## Stage 5 addendum — there are two cache layers

The two runs disagree on cold-compile cost:

| Run | cold wall | per pipeline | driver reported |
|---|---|---|---|
| first ever | 89.10 ms | 1.86 ms | 88.52 ms |
| repeat | 10.70 ms | 0.22 ms | 9.92 ms |

Both had an **empty `VkPipelineCache`** and both reported `cache_hits: 0`.
The 8x gap is therefore not our cache — it is **Mesa's own on-disk shader
cache**, which persists across processes independently of anything the
application serialises.

Stage 5 consequences:

- The honest cold-start number is **89 ms / 1.86 ms per pipeline** — first
  run on a given device, nothing warm anywhere.
- A `VkPipelineCache` blob still buys the remaining ~64x on top (10.70 → 0.17 ms).
- **Two caches must be versioned and shipped, not one.** Mesa's shader cache
  is keyed on its own driver build; the pipeline cache blob is keyed on
  `pipelineCacheUUID`. Invalidating one does not invalidate the other, and a
  benchmark that ignores the Mesa cache will overstate how cold "cold" is.

The blob came out **byte-identical at 244,765 bytes across all three runs**.
That determinism matters: a cache blob can be built once, checksummed, and
shipped, with a mismatch meaning a genuine environment change rather than
run-to-run noise.
